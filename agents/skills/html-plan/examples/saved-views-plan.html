Saved incident views

Users can save the filters of the incident list under a private name and open them again with one click. A saved view keeps only the filter part of the page address, so the page address stays the one place for filter settings.

Outcome
Searches that users do frequently open with one click.
Scope
Private views with names only. No sharing.
Approach
Three phases, in this order: storage, controls, release.
Limit
The page address stays the one place for filter settings.

Scope

Included

  • Make, open, and delete a private view, and change its name.
  • Keep the owner, the name, the filter text, and the time of each change.
  • Show which view is open. The filter controls stay as they are.
  • All controls continue to work with the keyboard and on small screens.

Not included

  • Views that other users or teams can see.
  • Permissions, pins, sort order, or folders for views.
  • Changes to how filters or the incident search work.
  • Changes to bookmarks that users already have in their browsers.

How a view works

  1. The user sets filters on the incident list and clicks Save current view.
  2. The server keeps the name and the filter text for that user.
  3. When the user opens the view, the incident list loads that filter text. The current filter code shows the results.

Phases

  1. Store private views

    Add a database table for views, with one owner for each view. Add server functions to make, list, change, and delete views. Only a signed-in user can use them.

    • Do not let one owner have two views with the same name.
    • Send each view only to its owner.
    • Keep the filter text as it is. Do not split it into separate fields.
    Done when
    Tests of the server functions cover owners, duplicate names, incorrect filter text, and delete.

  2. Add the save and open controls

    Put a list of saved views next to the filter controls. Put a save button in the filter panel.

    • The user can always see and change the current filters.
    • Use a dialog box only to give or change a name.
    • When the dialog box closes, move the keyboard focus back to the control that opened it.
    Depends on
    Store private views, with its final error messages

  3. Test and turn on

    Test the full feature while it is behind the current on/off switch for accounts. Then turn it on for internal users.

    Depends on
    Add the save and open controls
    To undo
    Turn off the switch. Saved views stay in the database and do nothing. You can keep them.

Decisions and risks

Decisions

  • Keep the filter text from the page address. The current code already reads it, checks it, and uses it for browser history and bookmarks.
  • Views are private in this release. Each view has one owner. Shared views and permissions are not in this plan.
  • Use the current on/off switch for accounts. You can turn the feature off at any time, and no new release tool is necessary.
  • Rejected: keep each filter in a separate field. This copies the filter rules into a second place. Then each change to the filter rules needs a database change.

Risks

  • Saved filter text can become old when the filters change. The incident list ignores filters that it does not know. The server refuses filter text that the current code cannot read.
  • Long names do not fit in the list. Names have a limit of 60 characters. Screen readers still get the full name.

Open question: can a user set a saved view to open by default?

This is not decided. This release does not include it, so the incident list keeps its current default filters.

Checks before release

  • A user can make, open, and delete a view, and change its name.
  • A different user cannot read or change that view.
  • Opening a view gives the same filters that the user saved.
  • The browser back and forward buttons work.
  • All steps work with the keyboard only.
  • The list and the dialog box fit on a screen 390 pixels wide, with no sideways scrolling.
  • Bookmarks that users already have work as before.
  • When the switch is off, no new control shows.
